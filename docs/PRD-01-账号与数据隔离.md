# PRD-01 账号体系与数据隔离（MVP 开发版）

版本：v1.0 ｜ 所属阶段：W1–W2（阶段 B 地基）｜ 关联文档：产品方案第 5.6、6.3、6.6 节
状态：可进入开发；标注「待定」的点在开工第一次评审时确认，不阻塞表结构设计。

---

## 1. 目标与范围

### 1.1 要解决的问题
通用平台下每个人只能看到和编辑自己的材料、草稿、模板；注册登录是所有业务接口的前置门槛；为后续 AI 调用、模板库、实体表提供归属主体。

### 1.2 本期做（In Scope）
- 邮箱 + 密码注册、登录、退出、当前用户信息获取。
- 会话保持（HttpOnly Cookie Session），登录态过期/失效的统一处理。
- 所有业务数据强制 `user_id` 归属与服务端越权拦截。
- 注册/登录错误提示与表单校验。

### 1.3 本期不做（Out of Scope，登记后续）
- 手机号验证码登录、微信/第三方 OAuth 登录。
- 找回密码、邮箱验证邮件流程（本期先用简单重置：预留接口位，不发邮件；如开发成本低可加，否则 W2 后补）。
- 个人资料编辑、头像、昵称体系（本期展示邮箱前缀即可）。
- 账号注销（只做停用标记预留，不提供用户自删入口）。
- 多角色权限、团队、分享协作。
- 会员等级与付费权益（只在 users 表预留 `plan` 字段）。

## 2. 角色与前置条件

| 角色 | 说明 | 进入条件 |
| --- | --- | --- |
| 未注册访客 | 只能访问注册/登录页 | — |
| 已注册普通用户 | 访问自己名下全部业务功能 | 登录成功，服务端签发会话 |
| （系统/开发视角）越权请求者 | 构造他人资源 ID 请求 | 必须被服务端拒绝并记安全日志 |

前置依赖：数据库 users 表与隔离中间件先于材料库接口落地；前端路由守卫在接口未就绪时只做页面拦截，真实安全以服务端为准。

## 3. 功能需求

### FR-A01 注册
- 触发：访客在注册页输入邮箱、密码、确认密码，提交。
- 输入校验（前后端都做，服务端为准）：
  - 邮箱格式合法；长度 ≤ 120 字符。
  - 密码 ≥ 8 位、≤ 72 位；至少包含字母和数字（不强制大小写/符号，降低注册门槛，但提示强度）。
  - 两次密码一致。
- 系统行为：
  - 邮箱已注册 → 返回明确错误「该邮箱已注册，可直接登录」，不透露用户其他信息。
  - 通过校验后创建 users 记录：密码使用 `argon2` 或 `bcrypt` 哈希存储，绝不存明文；`plan` 默认 `free`；`status` 默认 `active`。
  - 注册成功后自动登录（签发会话），跳转到工作台首页；不发验证邮件（本期）。
- 用户可见结果：进入工作台；右上角显示当前邮箱前缀与退出按钮。
- 异常与恢复：数据库写入失败 → 提示「注册失败，请稍后重试」，保留已填表单，不创建半条记录。

### FR-A02 登录
- 触发：登录页输入邮箱 + 密码提交。
- 系统行为：
  - 用户不存在或密码错误 → 统一提示「邮箱或密码不正确」（两者不区分提示，防止枚举账号）。
  - `status` 非 active → 提示「账号不可用，请联系支持」。
  - 校验通过 → 创建服务端 Session，下发 `HttpOnly` + `SameSite=Lax` + `Secure`（生产 HTTPS）的 Cookie；Cookie 不暴露给前端 JS。
- 用户可见结果：登录成功跳工作台；登录失败停留在登录页并提示。
- 安全细节：连续失败不做复杂限流也至少记录日志；本期可先加简单失败次数日志，不做验证码（待定，若上线后面临刷注册再加）。

### FR-A03 退出登录
- 触发：右上角退出按钮。
- 行为：服务端销毁当前 Session；前端清空本地状态；跳转登录页；刷新不可恢复登录态。

### FR-A04 当前用户信息与会话校验
- 前端加载任何业务页面前调用 `GET /me`；未登录/会话过期 → 清除前端状态并跳转登录页。
- `GET /me` 返回：`{id, email, emailPrefix, plan, createdAt}`；不返回密码哈希、密钥等任何敏感字段。
- 会话过期在页面内的表现：接口统一返回 401，前端统一弹「登录已过期，请重新登录」并跳登录页，不出现白屏或数据错乱。

### FR-A05（预留，不实现界面）修改密码
- 数据层预留 `password_hash` 更新能力；本期不做入口，避免扩大 W2 范围。

## 4. 数据模型

### 4.1 users 表

| 字段 | 类型（建议） | 约束 | 说明 |
| --- | --- | --- | --- |
| id | uuid / bigserial | PK | 服务端生成，不暴露给前端做业务判断 |
| email | varchar(120) | 唯一索引、非空、小写化存储 | 注册前统一 `trim().toLowerCase()` |
| password_hash | varchar(255) | 非空 | 仅存哈希 |
| email_prefix | varchar(60) | 可空 | 展示用冗余字段，可由邮箱派生，不必强制存 |
| plan | varchar(16) | 默认 `free` | free / pro 预留，本期不写入其他值 |
| status | varchar(16) | 默认 `active` | active / disabled；本期不提供置入口 |
| created_at | timestamptz | 非空 | 注册时间 |
| last_login_at | timestamptz | 可空 | 最近登录时间，登录成功时更新 |

### 4.2 全部业务表的隔离约定（强制）

- 材料、草稿、模板卡、实体、模型 Key、导出记录等表一律含 `user_id`（FK → users.id，非空索引）。
- 服务端每个查询都必须带 `WHERE user_id = currentUserId`；禁止前端传「当前用户 id」决定数据范围。
- 资源读取/修改/删除接口先查记录归属，归属不符统一返回 404 或 403（建议统一 404，避免暴露资源存在性）。
- 种子/内置数据（如内置模板卡）`user_id = NULL`，按「系统只读、人人可读、不可改」处理；个人数据 `user_id` 必填。

### 4.3 会话存储方案（二选一，开工定）
- 方案甲（推荐）：服务端 Session 存 PostgreSQL（sessions 表 + Cookie 存 sid），可服务端主动失效，契合已有 PG 技术栈。
- 方案乙：JWT 存 HttpOnly Cookie；实现轻但失效管理较弱。本项目选甲，便于后期强制下线与审计。

## 5. 接口定义（REST 草案）

统一响应：成功 `{data}`；失败 `{error:{code,message}}`；不回显堆栈与敏感信息。

| 接口 | 方法 | 入参 | 行为 / 主要错误码 |
| --- | --- | --- | --- |
| `/auth/register` | POST | email, password, confirmPassword | 成功 201；参数错 400；邮箱已存在 409 `EMAIL_TAKEN`；服务错 500 |
| `/auth/login` | POST | email, password | 成功 200 并种 Cookie；凭证错误 401 `INVALID_CREDENTIALS`；账号停用 403 `ACCOUNT_DISABLED` |
| `/auth/logout` | POST | 无（带 Cookie） | 销毁 Session；204/200 |
| `/me` | GET | 无 | 已登录返回用户信息；未登录 401 `UNAUTHORIZED` |

业务接口（材料/草稿等）统一由鉴权中间件包裹：未登录 → 401；登录但资源不归属 → 404 `NOT_FOUND`。

## 6. 页面与交互

- 登录/注册为独立极简页面（不显示主框架导航）；左右居中卡片，邮箱、密码输入框带 label；错误显示在表单下方，红色文字。
- 主框架顶部右侧：当前用户标识（邮箱前缀）+ 退出；未登录访问任何 `/app/*` 路由直接重定向 `/login`。
- 注册成功、登录失败、退出后跳转均给一次轻提示（沿用初代 toast 风格）。
- 不做找回密码链接的真实流程时，该链接不显示，避免无效入口。

## 7. 验收用例（开发完成逐条过）

### 成功场景
| 编号 | 步骤 | 预期结果 |
| --- | --- | --- |
| A-OK1 | 新邮箱注册，密码符合规则 | 注册成功、自动登录、进入工作台、数据库有 users 记录且密码为哈希 |
| A-OK2 | 已注册邮箱正确密码登录 | 登录成功、Cookie 种下、`GET /me` 返回正确用户信息 |
| A-OK3 | 登录后刷新页面、直接访问业务路由 | 保持登录态，进入对应页面 |
| A-OK4 | 退出登录后点浏览器后退/刷新 | 回到登录页，无法看到业务数据 |
| A-OK5 | 用户 A 创建一条材料后退出，用户 B 登录 | B 列表看不到 A 的材料（材料库联调时覆盖） |

### 失败与边界场景
| 编号 | 输入/操作 | 预期结果 |
| --- | --- | --- |
| A-F1 | 邮箱格式错 / 密码过短 / 两次不一致 | 前端拦截提示；绕过前端直接调接口服务端同样 400 |
| A-F2 | 注册已存在邮箱 | 409 明确提示，不创建重复记录 |
| A-F3 | 错误密码 / 不存在邮箱 | 统一「邮箱或密码不正确」，不区分账号是否存在 |
| A-F4 | 未登录直接请求业务 API | 401，前端跳登录页，不下发任何业务数据 |
| A-F5 | 用户 A 手动把材料/草稿 ID 换成 B 的 ID 请求 | 404，读不到也改不了；记录一条安全日志 |
| A-F6 | 数据库异常时注册 | 不产生半成品用户记录，提示可重试 |
| A-F7 | 会话过期后提交一个写操作 | 401，提示重新登录，且不发生写入 |

### 自动化测试要求
- 注册/登录/退出接口测试覆盖 A-OK1~OK4、A-F1~F3。
- 隔离测试用两个用户种子数据，遍历材料、草稿两类资源的读/写/删越权用例（A-F5）。
- 密码哈希校验：数据库中不出现明文密码；错误哈希登录失败。

## 8. 技术实现要点

1. 后端鉴权中间件统一从 Cookie 解析 Session → 当前用户对象 → 挂到请求上下文；业务代码只从上下文取 `userId`，不自行解析 Cookie。
2. 密码哈希算法参数成本选择开发环境可接受（bcrypt cost≥10 或 argon2id 默认参数）；迁移测试时确认登录耗时不卡顿。
3. 会话表结构：`sid, user_id, expires_at, created_at`；定时清理过期 Session；Cookie 设合理有效期（如 7 天滑动续期，本期可简化为固定过期时间）。
4. 所有 SQL/ORM 查询封装「用户作用域」查询方法，从机制上减少遗漏 `user_id` 的机会；Code Review 时重点检查裸 SQL。
5. 错误响应统一结构；安全日志记录时间、用户、接口、结果码，不记录密码与材料正文。
