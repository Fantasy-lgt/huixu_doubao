## 0. 一页读懂（先看这页）

**做什么**：帮职场人把散落在各处的月度/年度材料沉淀到个人材料库，用对话或表单两种方式触发整理，AI 按用户自己的模板体系生成带出处可核对的汇报 PPT，支持跨期追溯和年度汇总。

**一句话定位**：不是又一个「输入一句话出漂亮 PPT」的通用生成器，而是「个人材料库 + 自有模板体系 + 可溯源汇报初稿」的工作台。通用 PPT 生成赛道已有 Gamma、WPS AI、Kimi PPT 等强手，个人作品的差异化和面试讲解点应放在**材料沉淀、来源可溯、模板复用规则、多模型适配、多账号隔离**这些能讲清工程取舍的地方。【建议，依据见第 10 节】

**现在手里有什么**：初代 v0.1 已经跑通「选期间 → 导入材料 → 本地规则整理三章节初稿 → 人工核对确认 → 导出可编辑 pptx」完整闭环，且带来源逐字引用校验、乐观锁、原子写、外发确认、失败不丢稿等防护设计。这套**业务逻辑内核可复用**，缺的是账号、云端存储、AI 生成、模板库、好的编辑器界面和商业化预留。【事实，来自源码与验收文档】

**最关键的三个取舍（建议先认同再往下看细节）**：

1. **先做「可演示、可讲清」的 MVP，不一次做齐 16 条想法**。模板无损套版、自由画布、全自动年度实体统计、完整会员支付都放到后期；先用确定性工作流把核心闭环再做一遍并搬到云端。
2. **模板库分三阶段**：先做「模板卡片 + 规则匹配」（可控、能做完），再做「真实母版占位符受控填充」（需技术验证），「任意 PPT 自动拆解无损套用」不作为承诺目标（OOXML 复杂度决定个人项目做不稳，理由见 5.3）。
3. **技术栈向你的真实经验靠拢**：前端 Vue3、后端 Node.js 分层 + PostgreSQL，复用初代的 pptxgenjs 导出逻辑；RAG/向量检索、Agent 编排这类简历外能力只做轻量探索项，不背进 MVP 主线。

**接下来需要你拍板的 4 件事**（详见第 12 节）：首发形态与目标时点、模板库第一版深度、服务器预算口径、是否接受分阶段节奏。

## 1. 现状盘点：初代项目到底做到哪了

### 1.1 已确认的事实（来自实际界面、源码与 docs 验收文档）

| 模块 | 初代已实现能力 | 实现方式 |
| --- | --- | --- |
| 材料库 | 标题、月份、部门、正文、来源名；粘贴 + TXT/MD 导入（单份 2 万字内）；关键词搜索、部门/月份筛选；虚构示例一键加载 | state.json 单文件存储，重复期间+正文去重 |
| 汇报工作台 | 选月份/部门/本地或AI模式；本地规则按「重点进展/问题风险/下期计划」三段归集；条目可改文字、上下移、删除、人工补充；每条可跳原文核对；确认后导出 | 确定性规则整理（domain.cjs）；条目带 sourceIds + evidence 逐字摘录，服务端校验 quote 必须是原文子串 |
| 年度回顾 | 选年份+截至月份+部门，12 个月覆盖格（有料/缺月/范围外互斥），缺月不冒充完整年度；年度稿按月分组，不跨月累加成果 | 服务端确定性过滤与分组 |
| 模板与数据 | 固定模板可配单位名/主色/页脚，HTML 封面预览；JSON 备份/恢复/清空；AI 连接状态展示 | pptxgenjs 单母版（左侧色条+页脚+页码），纯文本可编辑对象 |
| AI 通道 | 预留 OpenAI 兼容 `/chat/completions`：env 配置 URL/模型/Key；调用前必须勾选「材料已脱敏并获准外发」；只发本次所选材料；输出结构与逐字引用不过校验则整份拒绝、保留原稿；不自动重试收费生成 | ai.cjs，无流式、无记忆、无工具调用 |
| 工程防护 | 仅绑 127.0.0.1；Host/Origin 校验；CSP；写操作带 baseRevision 乐观锁冲突返回 409；串行原子写（临时文件 rename）；21+ 项 node:test 自动测试 | server.cjs / store.cjs |

### 1.2 已明确没有做、也未验证的边界（不能在新方案里说成已有能力）

- 无账号、无多人、无数据隔离；数据是单文件 `data/state.json`，共享电脑他人可读。
- 无数据库、无向量检索、无长期记忆；「记住用户写作习惯」目前只是愿望。
- 不支持 Word / PDF / PPTX 原文件解析，只能粘贴纯文本；无图表、无版式库、无真实母版套版。
- 真实 AI 未联调过（无 Key，仅本机模拟接口合同）；真实 PPT 未在 PowerPoint/WPS 实机打开验收（离线渲染器看过版式）。
- 无支付、无水印机制、无多模型选择、无移动端适配、无小程序/桌面端。

| 来源 | 用户原话要点 | 对应需求 |

## 2. 目标用户与产品定位

### 2.1 目标用户分层（通用化后）

- **首要人群**：中小企业行政/综合/人力/内勤岗、项目助理、销售内勤——定期要写月报、周报、年度总结、述职、管理会汇报，手上材料分散、单位或自己有固定格式要求。
- **次要人群**：个人求职者/自由职业者沉淀自己的项目材料与汇报作品集；学生做课程汇报、答辩材料。
- **后期人群**：小型团队或小企业私有化部署（本期不做功能，只预留架构可能）。

### 2.2 核心使用场景（Jobs to be Done）

1. 月初/月末：把各来源文字材料丢进来，半小时内得到一份结构完整、出处可查、可直接套自己模板的汇报初稿。
2. 写稿时：用一句话告诉助手「整理 10 月管理会材料」，助手自动选材料、列大纲、缺什么追问什么，而不是让人翻菜单。
3. 年底：从全年材料里汇总年度总结，不再逐月翻聊天记录和旧文件。
4. 长期：材料、模板、常用写法沉淀在自己账号里，越用越顺手。

### 2.3 产品边界（本期不做什么，写死防止范围蔓延）

- 不做团队协作、共享空间、审批流（用户已明确本期不开团队共建）。
- 不做行业经营诊断、经营建议自动生成；只做材料汇总与表达辅助。
- 不做「上传任意复杂 PPT 母版一键无损学习」；只做受控模板方案（见 5.3）。
- 不做自由白板式无限画布排版（见 5.4.3 的评估结论）。
- 不做模型训练、不做 Agent 自动外发、不做无人审阅直接发送。

### 3.1 汇总：P0 / P1 / P2 清单

**P0（MVP v1.0，能上线演示的最小闭环）**
- 账号注册登录 + 个人数据空间隔离（#4 #16）
- 材料库改造：去部门、加类型/标签/标题检索（#10 #11）
- 保留并云端化初代核心闭环：选范围 → 整理初稿（本地规则可用、AI 可选）→ 来源核对 → 导出 pptx
- 飞书式三栏编辑器 + 显性步骤工作流（#12 的主体）
- 模板库 A 版：内置模板卡片 + 元数据匹配（#2 的 A 层、#3 的基础保存）
- 真实 AI 至少打通 1 家模型的受控生成（#14 的最小子集）

**P1（第一波增强，形成完整作品亮点）**
- 对话式指令助手（#1 完整版，含 3 选项追问）
- 模型适配层多模型选择 + 用户自带 Key（#14）
- 模板库：自定义模板元数据编辑 + 缺版式保存建议（#3）
- 年度回顾多维实体表与汇总导出（#9）
- PPT 逐页预览、多格式导出（PDF/图片，先评估再做）

**P2（后期探索与商业化）**
- 真实母版占位符受控填充 B 层（#2-B，先技术 Spike）
- 轻量版式拖拽微调（#12 画布的克制版）
- 会员权益、水印、去广告/看广告机制（#8）
- 私有化部署包（#4）
- 小程序端、桌面端、演讲稿生成、历史版本对比

**本期不做 ✕**：任意母版无损智能套版、自由无限画布、团队协作/共享、行业经营诊断、模型训练、Agent 自动执行外发操作。

## 4. MVP 范围定义（v1.0）

### 4.1 一期目标（已决策：约 8 周 / 2 个月，P0 全量 + 部分 P1）

让一个新用户注册后，能用两种方式（表单向导 / 一句话指令）完成：**导入若干份文字材料 → 得到结构化初稿 → 逐页核对修改 → 选择模板卡片 → 下载可编辑 PPTX**；自己的材料、草稿、模板互不串号，可备份导出。8 周内纳入的 P1 子集：对话指令助手简化版（意图识别 + 选项追问）、模型适配层接 1–2 家、年度实体表轻量版（人员/客户/合同三类，人工确认入库）。其余 P1/P2 不进本期承诺。

### 4.2 MVP 用户主流程（工作流，非自由画布）

```
注册登录 → 材料入库（粘贴/导入TXT/MD，选类型、打标签）
        → 选择任务（月度汇报 / 年度汇总 / 自由主题）
        → 助手确认参数（期间、类型范围、模板偏好；缺信息给选项）
        → 系统归集材料并生成大纲初稿（本地规则兜底，AI 可选增强）
        → 用户在三栏编辑器核对：左材料依据 / 中章节条目 / 右大纲与属性
        → 逐页匹配模板卡片 → 导出 PPTX（带出处标注）
        → 成品与材料沉淀回个人库，供年底汇总复用
```

### 4.3 验收口径（MVP 完成判定，提前写清楚，避免做到哪算哪）

1. 两个账号互相访问不到对方材料、草稿、模板（隔离用例自动测试覆盖）。
2. 无 API Key 时本地规则整理链路完整可用；配置 1 家 Key 后 AI 生成成功，且失败（鉴权/超时/坏结果）不污染原稿。
3. 导出 pptx 文本可编辑、模板卡片配色与标题生效；超长按规则分页或明确拒绝。
4. 材料可按类型/标签/月份检索；年度视图能列出覆盖月份与缺月提示。
5. 全程关键操作有状态反馈与失败恢复；备份可恢复。

## 5. 核心功能设计

### 5.1 AI 对话指令助手（对应 #1）

**产品形态**：工作台右上角常驻「问助手」入口；输入框 + 建议指令 chips；右侧抽屉对话，不打断主流程。

**工作机制（确定性优先，不靠自由聊天）**：

1. **意图识别**：把用户一句话映射到预置任务类型：月度汇报整理 / 年度汇总 / 材料检索 / 新建材料 / 模板推荐 / 导出设置。先用规则关键词 + LLM 结构化输出（JSON：`{intent, slots{year, month, types, keyword}}`），模型不可用时规则兜底。
2. **槽位追问**：必填槽位缺失（如没说月份、没说材料类型）时，助手一次问清，每个问题给 ≥3 个可点选项（最近月份、常用类型、常用模板），用户点选即可，不强迫打字。
3. **动作执行**：槽位齐全后调用既有后端工作流（选材料 → 生成大纲 → 进入编辑器），把过程显式展示：「已选 8 份材料，其中 3 份标注待补充，使用模板：月度汇报标准版」。
4. **异常分支**：找不到适配模板 → 给 3 个最接近模板卡并说明差异；材料不足 → 列出缺什么、建议从哪些月份补；用户可随时切换到手动表单。

**边界**：助手只调用白名单内的只读查询与草稿生成动作，不直接删除/导出/外发；涉及外发模型仍单独弹窗确认（沿用初代的安全设计）。

### 5.2 材料库改造（对应 #10 #11 #16）

数据字段演进（替代初代 Material）：

| 字段 | 说明 |
| --- | --- |
| id / userId / version | 归属账号与版本 |
| title | 材料标题 |
| materialType | 枚举类型：工作汇报/项目进展/会议纪要/人事行政/客户往来/合同商务/制度通知/其他 |
| tags[] | 自定义标签，多选 |
| period（YYYY-MM 或年度） | 归属期间；无明确月份的材料允许「未标记月份」但提醒 |
| occasion | 原「部门」字段改：汇报场合（月度管理会/例会/述职/项目复盘/其他），可空 |
| body | 原文，只读保留，不改写 |
| sourceName / createdAt / updatedAt | 来源与时间 |

交互：类型筛选条 + 标签云 + 月份时间轴 + 关键词搜索组合过滤；材料卡片显示类型色标、标签、期间、字数、来源。导入方式 MVP 仍以粘贴 + TXT/MD 为主；Word/PDF 解析放 P1（需引入解析库并做格式降级说明）。

### 5.3 模板库方案（对应 #2 #3，技术风险最高，单独展开）

#### 5.3.1 三层能力与现实边界

| 层 | 做什么 | 技术路线 | 可行性与限制 | 优先级 |
| --- | --- | --- | --- | --- |
| A 模板卡片库 | 每个卡片记录：名称、适用场景、页型标签（封面/要点列表3点/要点列表多点/数据图表占位/对比两栏/时间轴/结尾）、要点数、主色、字体规范、基于内置版式渲染 | 后端元数据 + 前端模板渲染器；匹配规则=大纲页需求（要点数、页型、主题）与卡片标签打分，LLM 仅在规则并列时辅助排序 | 高。完全可控，不碰真实 OOXML 复杂度 | **P0** |
| B 真实母版受控填充 | 用户上传一份自己的 pptx 母版，程序读取其 layout 与占位符，按页型白名单把文字/图表填进对应占位符，保留母版配色、母版图形、页脚 | python-pptx（或 Node 侧 docx 生态对等能力）解析 `slide_layouts`/`placeholders`；只写已声明占位符；输出保留母版主题 | 中。python-pptx 能打开模板、填占位符、加基础图表，但不支持全部 PowerPoint 特性（复杂动画、部分形状效果、SmartArt、高级图表样式）；且无法新增版式类型；WPS 与 PowerPoint 渲染有差异。必须先拿 2–3 份真实模板做 Spike 验证，不承诺「无损」 | P1 先验证，通过后再产品化 |
| C 任意母版智能拆解并自动匹配所有页型 | 上传任意 PPT，自动识别每页版式用途、自动匹配内容到任意页 | 需版式视觉识别 + OOXML 细粒度改写 | 低。生态成熟产品（WPS AI、Copilot）也只做到有限范围；个人项目不承诺 | ✕ 不立项，仅保留「未来观察」说明 |

#### 5.3.2 A 层匹配规则（可落地、可测试）

- 大纲生成时每页产出结构化描述：`{pageGoal, contentKind, itemCount, dataKind(text/bar/table), tags}`。
- 模板卡维护同样维度标签；匹配分 = 页型匹配分 + 要点数匹配分 + 场景/主题标签分；返回 Top3 供用户选，选中可替换。
- 柱状图等数据页：MVP 用内置图表版式（ECharts/PPT 原生图表占位）渲染；「锁定某母版特定图表样式」属于 B 层能力，P1 验证。

#### 5.3.3 自定义与保存建议（#3）

- 新建模板卡：选基础版式 → 填名称/场景/要点数/主色 → 保存到个人模板库。
- 当某次大纲页在库中无合适卡片时，编辑器右侧提示「当前页型暂无适配模板，是否把本次排版保存为新模板卡？」；用户确认后按当前页结构生成卡片草稿，可再编辑。
- 真正可视化拖拽改版式图形，P2。

### 5.4 PPT 编辑与输出平台（对应 #12）

#### 5.4.1 飞书式布局与步骤工作流

- 布局：左侧主导航（工作台/材料库/年度回顾/模板库/我的）；中间主编辑区；右侧上下文栏（当前页来源依据、大纲层级、模板属性、待补充项）。
- 显性工作流步骤条：①准备材料 → ②大纲与范围确认 → ③逐页内容核对 → ④模板匹配与版式 → ⑤导出。每步完成有状态标记；跳步时说明会回退哪一步。
- 草稿版本保留：重新生成不覆盖人工修改（初代已有版本机制，云端化后延续）。

#### 5.4.2 编辑器能力（MVP）

章节/条目增删改排序、来源跳转对照、待补充项高亮、页级预览（HTML 渲染近似效果，非真实 Office 渲染）、模板卡切换预览。

#### 5.4.3 画布评估结论（明确答复「要不要画布」）

**不做自由无限画布**。理由：核心价值是「内容可溯源、结构规整」，不是设计自由；自由拖拽排版工作量大、质量难控、移动端更难适配，且偏离求职作品集主线（可讲解的工程闭环优先于炫技交互）。
**替代方案**：逐页卡片式编辑器 + 右侧属性栏；P2 再评估「单页内文本块上下轻排序、配色切换」这类克制交互。若后续确有演示需要，可在单页预览内做局部拖动排序，而不是全画布。

### 5.5 年度回顾多维统计（对应 #9）

两层设计：

1. **材料维度统计（P0 已有基础上增强）**：按类型、标签、月份、来源场合统计数量与覆盖，图表用确定性聚合结果，不做业务结论推断。
2. **事实实体表（P1）**：预置三类实体表——人员（姓名、岗位、状态如退休/在职、变动月份、来源材料）、客户（名称、进展阶段、最近接触月份、来源）、合同/项目（名称、金额可空、阶段、起止、来源）。
   - 录入方式：用户手工增删改为主；AI 在整理材料时「建议候选条目」，人确认后入库（避免 AI 编造实体）。
   - 年度汇总：从实体表 + 材料表确定性查询生成名单清单和时间线，LLM 仅做措辞连贯化；每条保留来源材料引用。
   - 可扩展：后期用同一套实体表机制支持自定义实体类型（如设备清单、供应商），但 MVP 不做通用自定义建模器。

原则沿用初代文档：跨月同一事项不重复计为新增成果；缺失数据显式标「待补」；不自动算绩效结论。

### 5.6 账号体系与数据隔离（对应 #4 #16，架构地基）

- 账号：邮箱+密码（哈希存储，bcrypt/argon2）+ 邮箱验证码任选其一 MVP；登录态用服务端 Session 或 JWT，建议 Session + HttpOnly Cookie，前端简单、安全边界清楚。
- 隔离规则：所有查询服务端强制 `WHERE user_id = currentUser`；前端永不决定数据范围；模板卡分「系统内置（只读共享）」和「个人模板（私有）」两类。
- 文件（上传原文、导出 pptx、备份）：对象存储或本地磁盘按 `users/{userId}/...` 分目录，访问走服务端签名校验，不暴露直链。
- 隐私承诺界面：明确告知「使用外部模型时哪些内容会被发送、可关闭外发、可用纯本地规则模式」；对应初代已有的外发确认机制，云端保留并强化说明。

### 5.7 多模型与用户自带 Key（对应 #14）

- **模型适配层**：统一内部请求结构（messages、temperature、最大长度、流式开关），对每家 Provider 做请求/响应转换。DeepSeek、MiniMax、通义、智谱均提供 OpenAI 兼容协议，适配成本低；OpenAI 官方协议同源但国内网络需用户自备可达通道，界面标注提示。
- **Key 存储**：服务端加密存储（主密钥放环境变量，不入库明文）；前端只显示「已配置/未配置」和模型列表；密钥不进备份下载、不进日志、不出现在错误响应（沿用初代原则并强化）。
- **Key 缺失时**：提供「平台公共试用额度（可选，后期）」与「使用本地规则整理」两条路；MVP 先只支持用户自填 Key + 本地模式，不承诺平台代付额度。
- **调用控制**：每次调用前展示将发送的材料份数与范围；超时、401/403、429、坏 JSON 分类提示；不自动重试收费调用；记录本次调用耗时与状态（不含密钥与敏感正文）。

### 5.8 会员与水印商业化预留（对应 #8，P2）

MVP 只做两个不阻塞主线的预留位：导出文件带浅色「试用版」水印开关位；用户表预留 `plan` 字段。后期商业化时再评估：

- **会员功能候选**：去除水印、更多导出次数/页数、多模型可用、高级模板库、批量导出、优先生成队列。
- **免费解锁机制建议**：相比「看广告去水印」（PC 网页体验差、广告合规要求高），个人工具更适合「每日 N 次免费生成、完成新手任务解锁次数、邀请同行解锁」；广告位仅在移动版流量起来后再评估。
- **合规前置（后期做时必须办）**：用户协议、隐私政策、充值与退款规则、发票主体、备案（若域名面向国内公网）、内容安全提示。这些在有真实用户前不投入，先不写具体价格与承诺。

## 6. 架构设计

### 6.1 总体分层架构（示意，详见配套可视化 HTML）

```
[用户端]  Web/H5 浏览器（Vue3 + Vite）  …后期：Electron 桌面壳 / 微信小程序壳
    │ HTTPS
[接入层]  Nginx 反向代理 / 静态资源托管 / HTTPS 证书 / 限流
    │
[应用层 Node.js]
  ├─ 认证与租户隔离中间件
  ├─ 业务服务：材料服务 / 草稿与编辑器服务 / 模板服务 / 年度实体服务 / 对话助手编排
  ├─ 模型适配层（Provider 统一封装、Key 解密、调用预算与错误分类）
  └─ PPT 渲染服务（pptxgenjs 生成；后期 B 层接 python-pptx 微服务）
    │
[数据层]
  ├─ PostgreSQL：用户、材料、草稿、模板卡、实体表、版本记录、会员字段
  ├─ 文件存储：本地卷（单机版）/ 对象存储（云版）存原文附件与导出物
  └─ 向量检索（可选后期）：pgvector，仅用于历史材料语义召回，不作为汇总主依据
    │
[外部]  模型 API（DeepSeek / MiniMax / …）；邮件服务（验证码，可选）
```

### 6.2 技术选型与理由（结合真实能力，不堆简历外技术）

| 层 | 推荐选型 | 理由 | 备选与说明 |
| --- | --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite | 与既有前端经验一致；组件化后三栏编辑器好维护；Vue 生态有成熟表格/标签/上传组件 | 不选 React 重学成本；初代原生 JS 代码只迁移业务逻辑，不保留无框架结构 |
| 后端 | Node.js + TypeScript（Express 或 Fastify；结构清晰后可上 Nest） | 与初代 CommonJS 内核语言一致，整理规则/校验逻辑可直接移植；模型 SDK、pptxgenjs 都是 Node 生态 | 不引入 Java 重写（作品叙事不连贯、工期长） |
| 数据库 | PostgreSQL 15+ | 关系模型清晰（材料/草稿/模板/实体/用户）；后期加 pgvector 一个库兼顾，减少组件数 | 早期数据量小，也可用 SQLite 起步（单机版），上云再迁 PG，迁移成本可控 |
| PPT 生成 | 保留 pptxgenjs（卡片版式生成）；B 层另评估 python-pptx 微服务 | 初代已验证 pptxgenjs 可产出可编辑文本 pptx；python-pptx 生态对「读母版填占位符」更成熟 | B 层独立小服务，避免拖垮主服务稳定性 |
| 实时/流式 | SSE（已有经验：SSE 流式 AI 对话、上下文保持） | 对话助手与生成进度用 SSE 推送，和已有技能点匹配 | 不上 WebSocket 重型方案 |
| 部署 | Docker Compose（Nginx + 前端静态 + API + PostgreSQL + 存储卷） | 单机即可起全套，符合已有部署经验；后期私有化直接复用 compose 包 | 不在 MVP 上 K8s、微服务拆分、消息队列 |
| 向量检索 | P1 后期按需引入 pgvector | 历史材料语义召回辅助；非主线依赖，做不做由试用反馈决定 | 不用独立 Qdrant 增加运维面 |

**诚实提示【待验证】**：多模型统一适配、pgvector 用法、python-pptx 母版填充属于需要边做边查官方文档的部分；架构先把接口边界留好，每个能力先跑最小 Demo 再进主线，不在方案阶段假定已跑通。

### 6.3 数据模型演进（核心表，字段为设计草案）

- users：id, email, passwordHash, plan, createdAt, status
- materials：id, userId, title, materialType, tags, period, occasion, body, sourceName, fileRef, version, createdAt, updatedAt
- drafts：id, userId, kind(monthly/annual/free), rangeFilter, title, sections(JSONB), sourceRefs[], generationMode, confirmedVersion, version, createdAt, updatedAt
- template_cards：id, userId(null=系统内置), name, scene, pageType, itemCount, dataKind, palette, layoutRef, builtIn, createdAt
- entities（P1）：id, userId, kind(person/customer/contract), name, attributes(JSONB), period, sourceMaterialIds[], confirmedByUser, createdAt
- model_keys：id, userId, provider, encryptedKey, label, enabledAt
- export_jobs / watermark 字段（P2 预留）

所有表 `userId` 非空；草稿 sections 沿用初代「条目 + sourceIds + evidence」结构，保证已验证的溯源校验逻辑可移植。

### 6.4 关键安全与隐私设计

1. 外发最小化：模型请求只带本次任务选中材料，不带全库；外发前明示确认；本地规则模式完全不出网。
2. 密钥：服务端加密、不落前端、不进备份与日志。
3. 越权防护：每个写操作带归属校验；测试用例覆盖「账号 A 访问账号 B 的资源被拒」。
4. 内容安全：用户材料与 AI 返回都按不可信数据处理（初代 system prompt 的防注入思路保留并推广到对话助手）。
5. 备份：个人备份导出为加密/脱敏选项；备份不含他人数据与密钥。
6. 私有化形态：后期提供离线 compose 包，模型可换本地开源模型（如 Ollama 接入），满足「资料不出内网」诉求；本期只预留架构位置，不实现。

### 6.5 模型适配层内部结构

```
统一请求 {provider, modelKey, messages[], options{temperature, maxTokens, stream}}
  → Provider 适配器（协议转换 / 错误码映射 / 重试策略：仅对网络类错误重试一次，收费语义错误不重试）
  → 统一结果 {content, rawUsage, latencyMs, errorCode}
  → 输出结构校验（沿用初代：章节结构、来源归属、逐字引用校验）
```

#### 7.1.1 全新服务器采购建议（阶段1 落地用）

| 项 | 推荐 | 说明 |
| --- | --- | --- |
| 机型 | 国内主流云厂商轻量应用服务器 / 入门云服务器（阿里云/腾讯云/华为云同档比价） | 个人作品不需要企业级裸金属 |
| CPU/内存 | 2 核 4G 起步；预算允许直接 2 核 8G 更从容（PG + Node + Nginx 同时运行，4G 偏紧但可用） | 后期用户增多再升配，云厂商一般支持原地升配 |
| 磁盘 | 50G SSD 系统盘 + 单独数据卷（或直接 80G 系统盘），数据库与上传文件放数据卷 | 保证备份与扩容方便 |
| 带宽 | 3–5 Mbps 按固定带宽；前期演示流量小够用；后期按需升配或换流量包 | 不买大带宽闲置 |
| 操作系统 | Ubuntu 22.04 LTS（文档多、Docker 支持好） | 不选 CentOS 7 等已停更系统 |
| 运行形态 | Docker + Docker Compose 统一编排：nginx / web / api / postgres | 环境一致、迁移和重装容易 |
| 网络与备案 | 国内服务器绑域名必须先 ICP 备案（通常数周）；备案下来前先用 `IP:端口` 演示，或短期选用免备案节点仅做演示，正式对外再切备案域名 | 这条时间成本要提前排，别等到 W8 才处理 |
| 域名 | 1 个普通 `.com` / `.cn` 域名即可；HTTPS 用免费证书自动续期 | 不需要买多域名或高防护套餐 |
| 模型流量 | 模型调用走服务器出网到模型厂商 API，服务器本身不跑模型、不需要 GPU | 成本主要是 API 调用量，不是服务器算力 |

> 采购前先用一张测试材料在本机把 MVP 跑通，再下单服务器，避免服务没就绪先付月租。

### 7.2 必做的基础件（不论阶段）

- 域名解析 + HTTPS（Let's Encrypt 免费证书或云厂商免费证书）；
- 数据每日备份脚本（数据库导出 + 关键文件打包，保留最近 N 份）；
- 环境变量管理（密钥不入库、不进代码仓库）；
- 日志分级（错误日志不含密钥与材料正文全文）；
- 重启自恢复（compose restart policy）。

### 7.3 不需要一开始就买的东西

「全能服务器」「大容量云盘」「企业级 CDN」「多节点负载均衡」在个人作品早期都不需要；等出现明确用户量和瓶颈指标再升配，避免把有限预算花在闲置资源上（用户当前现金流紧张，这条尤其重要，先花时间少花钱）。

## 8. 多端演进路线（回答 H5 / 桌面端 / 小程序怎么做）

### 8.1 顺序建议：Web/H5 响应式 → 桌面端壳 → 小程序（最后且谨慎）

| 端 | 优先级 | 做法 | 理由 |
| --- | --- | --- | --- |
| Web（PC 浏览器） | **P0 首发** | Vue3 响应式，桌面为主、兼容手机浏览器窄屏（初代已做过窄屏适配经验可复用） | 核心流程涉及多文件、表格、长文核对，大屏效率最高；开发成本最低、作品集演示最方便 |
| H5 移动网页 | P1 | 同套前端响应式适配；移动端只做查看材料、对话查询、草稿浏览，复杂编辑留在 PC | 不单独写一套，靠响应式 + 移动端精简布局控制成本 |
| 桌面端 | P2 | 优先 Electron（Node 后端逻辑直接复用、生态成熟；安装包约 80MB 级）；若追求轻量再评估 Tauri（2–10MB 但需少量 Rust 学习成本） | 桌面端价值在于「本机文件读取、本地存储隐私版」，等 Web 版稳定、确有离线使用诉求再做；不要一开始就上桌面框架 |
| 小程序 | P2 后置，不建议首发 | 若做：uni-app（既有经验）一套代码到小程序+H5；但小程序限制文件大小、后台模型调用需合规域名备案与内容审核，离线材料管理体验受限 | 小程序适合轻查询/分享，不适合重型编辑；作品集阶段不必为它增加合规与审核成本 |

### 8.2 架构上为多端留的口子

- 前后端分离：所有能力走 JSON API，桌面壳和小程序只是不同前端壳，不重写业务逻辑。
- 上传、导出、认证等能力按端做适配层差异，核心服务不变。
- 桌面隐私版后期可复用初代「本机数据 + 可选外发确认」思路，和云端账号版共用渲染内核。

**B. 业务样本（开发中期提供即可，没有就先用虚构数据）**

6. 1–2 份脱敏真实汇报 PPTX 成品（隐去公司名、客户名、数字）：判断真实页型与篇幅。
7. 3–5 份典型原材料（月报/项目进展/客户走访纪要，脱敏）：确认格式分布与解析优先级。
8. 一份你期望的典型汇报大纲样例（章节、每页大概几条）：用于模板卡页型设计。
9. 真实场景频率（每月做几次、每次约几小时、最烦哪个环节）：校准痛点优先级。
10. 每周可投入开发的大致小时数与时段：把 8 周排期细化到可执行任务量。

### 12.3 你还没问到、但应该提前知道的几件事

- 「AI 记住写作习惯」不是接了大模型就自动有：它=可复用的模板偏好 + 常用句式库 + 历史确认稿索引，需要单独设计存储，MVP 先存「模板偏好 + 常用标题结构」，记忆能力分阶段加。
- 「年度企业维度统计」本质是建结构化数据表，不是让 AI 读一遍材料自动出名单；AI 只做候选建议，人确认后才成为数据，避免编造人员/客户信息。
- 「画布式自由编辑」听起来炫但工作量和维护成本高，建议克制；先把结构化编辑器做顺。
- 作品集面试时，面试官更关心你为什么这么选型、失败过什么、怎么验证，而不是功能数量；宁可 4 个功能讲透，不要 20 个功能讲不清。
