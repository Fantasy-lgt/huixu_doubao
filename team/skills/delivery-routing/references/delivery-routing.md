# 交付路由细则

> 本文件由 `AGENTS.md` 下沉。`AGENTS.md`「产物交付决策」保留 7 条顶层硬规则；本文件承载各分支的执行细则、数据来源与采用建议、`arch_type` 参数约束。冲突时以 `AGENTS.md` 顶层硬规则为准。

## `构建网页应用`工具 分支

- 报告用于汇报、演示、经营评审、市场进入评审、竞品对比讨论、管理层决策、对外展示、浏览或会议讨论时，调用 `构建网页应用`工具。
- 需要一眼看到关键结论、市场吸引力、竞争格局、玩家分层、机会风险、进入门槛或决策建议时，调用 `构建网页应用`工具。
- 用户要创意设计、官网、营销页、产品介绍页、可交互原型、UI mockup、线框图、应用界面、流程 Demo、dashboard、落地页、信息图、单页图表或其他可视化页面时，调用 `构建网页应用`工具。
- 用户要普通 PPT/PPTX/slides/deck/演示稿且未明确要求飞书原生幻灯片时，调用 `构建网页应用`工具，以网页演示文稿或在线 deck 交付。
- 用户要动画、3D、游戏、Canvas、SVG 或重动效视觉时，调用 `构建网页应用`工具；简单、单页或单图需求也不例外。
- 产业链图、竞争地图、技术路线图、趋势时间线、指标卡、对比矩阵、条件筛选、展开收起、来源展开或复制摘要等可以提高理解和决策效率时，优先在网页中呈现。
- HTML 不是正文截图或纯文本堆叠；应用图表、分区、指标卡、对比矩阵、来源展开、筛选或其他必要交互把结论可视化。
- 对话/评论里只放概览、关键结论和网页链接，不要把长正文重复贴进对话。
- 生成 HTML 的场景全部直接调用 `构建网页应用`工具；禁止先写一份 HTML 页面，再调用 `构建网页应用`工具传入。

## 数据来源与采用建议（网页、云文档与最终回复硬要求）

调用 `构建网页应用`工具或 `app_builder` 前，必须在传给子代理的 `user_prompt` 中附逐项 `fact_ledger`。每项记录：场景/主张、事实状态、来源、资料日期/适用范围、数据风险与限制、采用建议和核验方式。事实状态仅可为"已核验事实、待核验事实、虚拟示例、假设、理论推演、概念构想"；没有可访问来源的内容不得写成已核验事实。

**网页与飞书云文档的末尾必须有 `## 数据来源与采用建议`。** 这不是泛泛免责声明，而是对本次内容的可审计摘要；放在产物最后一个实质性章节，以表格列出 `场景/主张 | 事实状态 | 数据风险与限制 | 采用建议 | 核验方式`。每份网页和云文档至少保留一行：纯视觉、原创或无外部事实主张的产物也要写明"概念构想/虚拟示例"、不代表真实数据或已验证效果，以及可继续核验的材料。固定表头如下，必须用本次真实内容填充，不能保留占位符：

| 场景/主张 | 事实状态 | 数据风险与限制 | 采用建议 | 核验方式 |
| --- | --- | --- | --- | --- |
| 本次关键事实、数据、示例或方案 | 已核验事实/待核验事实/虚拟示例/假设/理论推演/概念构想 | 时效、样本、范围、来源或适用性限制 | 可直接使用/需你确认后使用/仅占位·勿据此决策 + 结合本次内容的一句话依据 | 原始 URL、用户材料、复算或待补验证动作 |

`采用建议` 只能使用三档，并且每格必须写成"枚举值 + 结合本次内容的一句话依据"，不得只填枚举词：

| 采用建议 | 判定标准 | 写法示例 |
| --- | --- | --- |
| 可直接使用 | 来自用户明确材料、可访问原始来源、确定的设计规范或有明确实现依据的产物状态；风险只影响时效或适用范围，不影响当前交付采用 | 可直接使用：品牌主色来自用户提供的设计稿，本页仅按该色值扩展 hover/暗色 token |
| 需你确认后使用 | 基于合理设计假设、行业惯例、信息架构判断或待核验资料；方向可用于评审，但上线前需要用户/业务确认 | 需你确认后使用：目标用户被假设为首次访问者，因此首屏优先解释价值主张，若实际是老用户运营页需调整信息优先级 |
| 仅占位·勿据此决策 | 虚拟示例、演示数据、概念构想、未接入真实接口或无法核验的效果推演；只能用于版式、交互或视觉占位 | 仅占位·勿据此决策：图表中的 3.2% 转化率为演示数据，只用于验证图表布局，上线前必须替换为真实埋点 |

不得再在数字、图表、段落或卡片旁机械添加 `【已核验】`、`【假设】` 等状态标签，也不得仅用页脚免责声明代替该末尾说明。

事实状态回答"这条内容是什么"，采用建议回答"用户该怎么处理它"：已核验事实写明原始来源与时效，并通常给出"可直接使用"；待核验事实写明缺失来源、时点或适用范围，并通常给出"需你确认后使用"；虚拟示例、假设、理论推演和概念构想写明其适用场景、不能据此作出的结论及下一步验证方式，并根据风险给出"需你确认后使用"或"仅占位·勿据此决策"。回读网页或云文档时，确认末尾表格可见、与 `fact_ledger` 一致；缺失、错误或来源失效时必须修正、删除或调整采用建议。

最终回复必须在核心结论和产物链接后增加简短的"数据来源与采用建议"，按本次内容分三类写明：哪些内容可直接使用、哪些内容需用户确认后使用、哪些内容仅占位且不能用于决策。不得再给单一总体等级，也不得把不同性质的事实、假设和示例平均成一个模糊判断；对话说明不能替代网页或云文档中的末尾表格。

## arch_type 参数约束（统一标准）

本节优先于其他关于 `arch_type` 默认值的旧描述。新建应用必须传入 `arch_type` 参数，按以下规则选择：

- 用户 query 明确指定类型时按其表述执行：
  - 出现 HTML 字样并以其为交付形式（如"用 HTML""生成 HTML 页面/代码""单文件""不用框架"）→ `html`。
  - 明确要求"全栈""数据库""后端 API""前后端""持久化存储""权限"或"鉴权"→ `fullstack`；明确要求"jspage"→ `jspage`。
  - "先做网页版""做成 H5"等未明确类型的表述只表示需要构建网页应用，继续按下方场景判定。
- 用户未明确指定时，先判断是否需要长期保存和管理数据或文件，或是否需要鉴权：明确需要 → `fullstack`；看似需要但未说清 → 先追问。
- 排除 `fullstack` 后：
  - 不调用 AI，且以展示或演示为主 → `html`，如官网、营销页、落地页、幻灯片、可视化报告、数据看板、可交互原型、流程 Demo、3D、游戏、Canvas、SVG 或重动画场景。
  - 数据看板、可视化报告等，即使包含筛选、切换、展开、排序或页面内编辑等弱交互，也仍应选择 `html`。
  - 需要运行时调用 AI，或以工具操作、功能流程为主 → `jspage`，如文本对比、价格计算器、随机分组、AI 文案生成器、简历优化器或会议纪要生成器。
- Agent 在构建阶段生成内容不算运行时 AI；拿不准 `html` 与 `jspage` 的区别时，优先选择 `html`。同一 query 同时命中多种类型且无法兼容时，先追问用户。
