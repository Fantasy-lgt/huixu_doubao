# 优先级与 Roadmap

优先级是资源约束下的取舍，不是表格算分。Roadmap 是对结果、依赖和学习顺序的表达，不是功能日历。

## 1. 先定义排序问题

明确：排序对象、要优化的结果、时间范围、不可违反的约束、共享资源和最终决策者。不同层级的事项不要混排，例如战略方向、问题机会、功能和技术债应分别比较。

## 2. 硬约束先于评分

先识别安全、合规、合同承诺、线上故障、基础依赖和不可逆窗口。硬约束不是因为“分高”而优先，也不应与普通增长功能放在同一总分里。

## 3. 选择最轻的方法

- 事项很少且取舍清晰：直接比较用户价值、业务价值、证据、成本、风险和依赖；
- 有可靠 reach、impact、confidence、effort：可用 RICE；
- 仅有 impact、confidence、ease：可用 ICE；
- 团队已有明确战略权重：可用加权评分；
- 依赖或时间窗口主导：先画依赖图或成本延迟关系。

缺任何必要输入时不计算总分；用“未知”和敏感性分析暴露它会如何改变排序。不要擅自给影响、信心、工作量或权重补默认值。

如需复算，可运行：

```bash
python3 scripts/score_priorities.py priorities.csv --method rice
```

脚本只计算输入，不判断事实是否可靠。

公式不可混用：

- `RICE = Reach × Impact × Confidence ÷ Effort`，Reach 必须有时间范围和人群口径；
- `ICE = Impact × Confidence × Ease`，它不包含 Reach，不能写成 RICE；
- 加权评分为 `Σ(分值 × 权重)`，权重和必须等于 100%。

每个输入都要说明量表、来源和方向。示例数字也必须通过脚本复算；无法解释取值时宁可做定性排序。

## 4. 给出真实取舍

每个推荐项说明：为什么现在、替代或推迟了什么、依赖谁、证据不足在哪里、什么信号会改变排序。对于不互斥方向，使用先后顺序、组合或分层选择，不制造假二选一。

## 5. 设计 outcome-driven Roadmap

每个阶段至少包含：

| 字段 | 含义 |
|---|---|
| 目标结果 | 用户或业务状态要发生什么变化 |
| 当前问题 | 为什么该阶段值得投入 |
| 关键行动 | 为验证或实现结果采取什么动作 |
| 依赖与容量 | 前置能力、共享资源及其确认状态 |
| 结果信号 | 如何知道方向有效 |
| 退出条件 | 何时进入下一阶段、暂停或回退 |
| 重排触发器 | 哪个新事实会改变计划 |

Now / Next / Later 适合时间不确定但顺序明确的场景；有真实日期和资源承诺时才写季度或月份。不要凭空分配工期、人力或百分比容量。

Roadmap 图应突出结果、依赖和门槛。甘特图只有在真实排期需要时使用，不能代替产品路线图。

## 6. 先算容量，再排承诺

路线图出现团队人数、迭代或季度时，先建立容量账：

`可用容量 = 团队人数 × 可投入比例 × 迭代长度 - 已确认固定负担`

可投入比例、会议、线上支持、请假、维护和共享依赖都必须来自用户输入或标为待确认。没有这些输入时只给公式、收集表和分配原则，不凭经验填百分比。容量分配至少区分承诺工作、维护/缺陷、探索和缓冲，并说明每一块挤占时替代什么。

需求治理方案按任务需要交付：

- 统一提报模板与进入需求池的 DoR；
- RACI 或逐节点责任表；
- 评审节奏、输入、输出和完成定义；
- RICE/ICE 的取值说明与可复算示例；
- 插单申请：原因、紧急等级、替换项、延期影响、批准者和同步对象；
- 风险预警信号、升级路径和变更记录；
- 面向管理者的沟通口径：保留决策权，同时把插队成本和被替换承诺显性化。

## 7. 定期重排

在阶段退出、关键数据更新、资源变化、依赖延期或风险暴露时重排。保留变更记录：改了什么、基于什么新事实、受影响的承诺、谁作出决定。
